 1. 產品概述
1.1 產品簡介
「攜手基地」是一套支援線上同儕活動的服務管理流程與互動原型。服務團隊使用既有多人線上遊戲承載共同活動，並以產品介面支援參與者報名、需求確認、固定小組安排、活動資訊取得、問題回報、活動回饋及結束後追蹤。
產品不負責開發遊戲本體，也不取代既有遊戲、語音／文字通訊工具或專業支持服務。產品的核心價值是讓一項以人為主導的同儕活動服務具有一致、可追蹤且可管理的操作流程。
1.2 產品問題
成年行動障礙者可能因移動、交通、場地可及性或外出安排而較難穩定參與實體同儕活動。一般線上遊戲社群雖提供遠端互動空間，但參與者通常仍需自行尋找社群、理解規則、協調活動及處理互動問題。本產品要補上的服務流程，是將固定成員、持續共同活動、明確管理與活動後追蹤整合成可執行的服務。
1.3 產品目標
•	讓符合條件的參與者能理解服務內容、提交參與需求並完成入組流程。
•	讓服務團隊能依參與需求安排固定小組、發布活動資訊並管理場次。
•	讓參與者能使用清楚的方式取得活動資訊、加入共同活動、尋求協助及提供回饋。
•	讓服務團隊能以一致的方式記錄報名、出席、問題處理及參與者回饋。
•	讓 PoC 演示一條完整、可點擊且有狀態變化的使用者旅程。
1.4 非目標（Out of Scope）
•	自行開發遊戲、遊戲引擎、遊戲內外掛或即時配對演算法。
•	建置完整的即時聊天、語音通話、視訊、支付或公開社交網路。
•	提供心理治療、醫療評估、診斷或臨床成效保證。
•	在 PoC 階段建置正式生產環境、實際第三方帳號整合或自動化通知服務；可用模擬狀態展示。
•	規定資料庫 schema、API、技術堆疊、部署架構或 UI 視覺規範；這些屬於後續設計與實作決策。
產品成功的核心判斷
評估產品是否能協助服務團隊把「招募與入組 → 固定小組活動 → 問題處理與回饋 → 後續追蹤」完整跑通。活動是否形成友誼是服務成效問題，需以參與者互動資料與回饋另行評估。

2. 服務對象與使用者角色
2.1 服務對象定義
本案服務對象為年滿 18 歲，因肢體障礙或其他持續性移動功能限制，實際上較難外出或穩定參與實體同儕活動的成人。參與確認應聚焦於活動參與需求、設備與操作方式、可用時段及所需協助；不要求參與者在社群內公開診斷或醫療資訊。正式試辦前，服務團隊應再確認招募與納入條件。
設計依據：Trepte、Reinecke 與 Juechems（2012）以 811 名電子競技社群成員為研究對象，分析線上遊戲中的社會資本與線上、線下社會支持之關聯。此研究支持將固定成員、持續互動與遊戲外自願聯繫納入產品設計考量。DOI: https://doi.org/10.1016/j.chb.2011.12.003

2.3 使用者需求（Jobs to Be Done）
•	參與者：我希望用可行的操作方式參加固定團體，不必自行尋找陌生社群或獨自處理所有安排。
•	參與者：我希望事先知道活動目標、時間、加入方式、互動規則，以及遇到問題時可以找誰。
•	服務管理者：我希望能快速掌握誰已報名、誰需要協助、每個小組何時活動，以及哪些事項尚待處理。
•	服務管理者：我希望能將活動執行情況與參與者回饋連結，據以安排後續場次及檢視服務結果。
3. 產品範圍與版本規劃
3.1 PoC 定義
本次交付目標為可互動的 UI PoC。PoC 必須讓使用者能點擊主要操作、看見不同狀態及完成一條端到端流程；底層資料可由模擬資料提供，外部整合可以用示意結果呈現。原型中凡屬模擬的通知、遊戲連線、表單送出或資料更新，都應在開發文件或展示說明中清楚標示。
3.2 PoC 必須涵蓋（Must Have）
功能區域	PoC 必須展示的能力
服務說明與報名	查看服務目的、對象、參與流程及規則；填寫報名與參與需求；看到送出結果。
申請管理	管理者可查看模擬申請、更新申請狀態、記錄需補充確認的事項。
參與方式確認	呈現設備、遊戲經驗、文字／語音偏好及操作協助需求的確認結果。
固定小組與活動	管理者能安排小組與活動時段；參與者能查看所屬小組、場次、任務及加入指引。
問題回報	參與者能選擇問題類型並提交回報；管理者能查看、更新處理狀態。
活動紀錄與回饋	管理者可登記出席；參與者可提交活動回饋；系統能顯示紀錄已完成。
後續追蹤與摘要	能進入結束後追蹤畫面，並查看基本服務數據或摘要。

3.3 後續試辦可納入（Should / Could Have）
優先級	功能	納入條件
Should	活動前提醒與參與狀態通知	已確定通知管道，且有助於降低漏看活動資訊。
Should	管理者匯出參與／回饋摘要	試辦團隊需要定期彙整成果或向支持者報告。
Could	自助修改可用時段與互動偏好	固定小組與排程流程已穩定，且資料變更不會造成額外管理負擔。
Could	活動任務範本庫	累積足夠活動經驗後，再整理可重複使用的任務設計。

3.4 不納入本次 PoC
•	真實身分驗證、遊戲帳號自動串接、即時遊戲狀態讀取及自動化遊戲內管理。
•	即時私訊、社群配對、AI 推薦成員、情緒判讀、風險預測等進階功能。
•	向參與者公開完整聊天紀錄或以聊天內容自動判定友誼強度。
4. 核心使用者旅程
4.1 參與者端到端流程
產品支援兩個相連的旅程：先完成招募與入組，再透過固定小組的重複活動形成持續服務。流程中的審核、分組、活動主持與安全事件處理由服務團隊負責；產品提供操作入口、狀態、紀錄及回饋。

入組後，每次活動應重複使用一致的通知、加入、共同任務、回饋與紀錄流程；活動中遇到的技術或安全問題會進入獨立的處理流程。
 
圖 2｜固定小組的每週活動循環
4.2 管理者主要流程
1.	建立本期招募資訊與預計活動時段。
2.	查看新申請，確認參與條件、聯繫需求與參與者同意狀態。
3.	確認設備、操作及互動偏好；若仍有障礙，先協調調整或替代參與方式。
4.	將參與者安排至固定小組，建立場次、共同任務及加入指引。
5.	活動前確認主持人、任務與安全規則；活動後記錄出席、問題與簡短回饋。
6.	檢視參與與回饋摘要，安排下一場活動或啟動結束後追蹤。
4.3 活動中問題處理流程
產品應支援兩種主要事件路徑：技術問題由主持人協助排除，或提供替代參與方式；安全事件則先停止不當互動、保護受影響參與者，再由管理者記錄處理狀態與後續安排。不得要求參與者在公開群組中說明敏感細節。

7. 業務規則與服務政策
規則 ID	規則	產品行為要求
BR-01	成年資格	服務對象需年滿 18 歲；具體報名資格由服務團隊依正式招募說明確認。
BR-02	參與同意	參與者在查看必要規則並同意參與方式後，才進入正式安排狀態。
BR-03	固定小組	參與者原則上安排於固定小組，以支持持續互動；任何調整由管理者記錄原因與結果。
BR-04	平台可及性	分組前應確認設備與操作方式；未確認者須保留待處理狀態，不能直接視為已能參與。
BR-05	參與方式選擇	文字互動與語音互動偏好應被尊重；不得把開啟語音作為唯一參與方式，除非活動本身有明確且必要的要求並事前說明。
BR-06	私人空間與權限	活動空間採邀請或經確認後加入的方式；加入資訊只提供給已安排的參與者。
BR-07	安全處理	主持人可暫停活動、限制不當互動或移除違規成員；事件需有管理者後續紀錄。
BR-08	活動外聯繫	活動外私下交流應由參與者自願決定；產品不得將分享個人聯絡方式設為必要條件。
BR-09	資料最小化	只收集安排、執行及評估服務所需的資料；不蒐集與服務無關的醫療細節。
BR-10	PoC 資料	展示用資料須為虛構或已去識別的測試資料；不得把真實參與者個資放入公開展示。

8. 非功能需求（Non-functional Requirements）
類別	需求	驗收／檢查方式
可及性	主要操作需有清楚文字標籤、可辨識的焦點狀態與足夠的文字可讀性；核心流程避免只靠顏色傳達狀態。	以鍵盤完成核心流程；檢查標籤、焦點順序、錯誤提示與文字縮放後的可讀性。
易用性	參與者應能理解目前狀態、下一步與求助方式。	在主要頁面確認有明確狀態與下一步；錯誤提示須指出修正方式。
隱私	個人聯絡資料與公開社群身分應盡量分開；管理者功能限授權角色使用。	檢查公開參與者畫面不會顯示管理備註、聯絡資料或事件細節。
安全	加入指引、社群規則、事件回報與管理者處理方式需一致。	測試參與者能找到規則與求助入口；管理者能追蹤事件狀態。
一致性	同一狀態在參與者與管理者端應有一致定義。	檢查申請、場次、問題及追蹤各狀態不互相矛盾。
回應與穩定	PoC 核心頁面切換與表單操作應保持流暢；狀態更新需有明確回饋。	手動驗收報名、狀態變更、回饋提交及主要頁面切換，不出現無回應的點擊。
可維護性	活動流程、參與規則與指標說明應可由產品／服務負責人理解並更新。	需求、頁面與驗收案例使用一致的功能 ID 或名稱。
誠實呈現	模擬的第三方整合、通知、遊戲連線與統計不得偽裝成已實際執行。	展示流程中可清楚區分實際可用功能、模擬資料與未實作整合。

9.1 指標呈現原則
•	所有比率都需標示分子、分母、統計期間及排除規則。
•	將「未回覆」與「負面回饋」分開；缺席不自動等同於不感興趣。
•	PoC 儀表板可使用假資料展示，不應把假資料標示為實際服務成果。
•	若後續採用標準化孤獨感或社會連結量表，需先確認中文版本、授權、使用條件及施測安排。
10. PoC 展示與驗收計畫
10.1 必須跑通的展示劇本
步驟	操作	通過條件
1. 參與者報名	以測試參與者查看服務資訊並提交報名與參與偏好。	送出後看見申請確認畫面；管理者端出現該筆測試申請。
2. 管理者確認	管理者打開申請，確認資格、互動方式與設備狀態，更新處理狀態。	申請狀態從「待確認」更新為「可安排」或「需後續聯繫」。
3. 安排小組	管理者指定固定小組、場次、任務與主持人。	參與者端可查看自己的小組與活動詳細資訊。
4. 加入活動	參與者查看加入指引及安全規則，進入活動資訊頁。	可看到加入方式、活動目標、時間及求助管道；若為模擬連線須有標示。
5. 回報問題	參與者提交一筆技術或安全問題。	參與者看到已收到；管理者端出現事件，且可更新處理狀態。
6. 完成活動回饋	管理者登記出席；參與者提交活動回饋。	出席及回饋紀錄可在管理者摘要中查看。
7. 結束後追蹤	管理者啟動追蹤；參與者提交測試追蹤回饋。	追蹤狀態更新，摘要頁顯示對應的模擬統計。

10.2 PoC 完成定義（Definition of Done）
•	所有 P0 需求至少有一個對應畫面或操作狀態。
•	測試者能從服務說明開始，依序跑完報名、管理者確認、分組、活動資訊、問題回報、活動回饋及後續追蹤。
•	所有主要按鈕有明確作用；任何不可用功能皆以禁用狀態或清楚提示呈現，不保留無效點擊。
•	報名送出、狀態更新、事件回報及回饋提交都有完成或錯誤回饋。
•	至少包含一般成功路徑、報名資料錯誤、待確認、技術問題及安全事件五種狀態。
•	展示使用的測試資料均為虛構資料，且模擬功能沒有被描述為已上線的真實整合。
•	以鍵盤可完成核心操作；文字標籤、錯誤訊息與狀態標示可辨識。
11. 依賴、風險與應對
項目	風險／依賴	產品或服務層面的處理方式
遊戲與設備可及性	不同裝置、操作需求及遊戲設定可能影響參與。	把設備與操作確認放在分組前；先做短測試；若不適用，記錄需調整而不直接進入正式排程。
活動主持量能	社群需要穩定主持與問題處理，單靠軟體無法代替人力。	在活動頁指定主持人及備援聯絡方式；管理者工作清單顯示待處理事項。
招募與出席	招募人數、時段匹配及持續出席可能影響固定小組運作。	管理者可查看可用時段及待確認名單；排程變更需能通知或明確標示。
騷擾與社群安全	多人線上互動可能出現冒犯、不當行為或隱私風險。	採受邀加入、明確規則、主持人可介入、事件回報與後續追蹤；不將責任全部交給參與者自行處理。
個人資料	報名資訊、聯絡方式及安全事件紀錄可能包含敏感內容。	採資料最小化、角色權限、測試資料去識別化，並限制公開頁面可見資料。
第三方工具依賴	遊戲、通訊或表單工具的可用性、價格及政策可能變動。	PRD 將需求與特定工具分開；正式選型前確認授權、可及性、隱私設定與費用。
PoC 與正式服務落差	可互動原型可能以模擬狀態展示，未連接真實服務。	展示時說明真實功能、模擬功能及待整合項目；正式試辦前需完成運作流程與資料處理檢查。

13. 交付成果與下一步
13.1 本 PRD 所定義的產品交付物
•	一組可互動的 UI PoC，支援參與者端與管理者端的主要任務。
•	一條可演示的端到端流程，包含成功路徑及核心例外狀態。
•	一組以虛構資料構成的示範案例，含申請、固定小組、活動、回報、回饋與追蹤紀錄。
•	需求對照驗收清單，能將每個 P0 需求對應至畫面、互動或測試步驟。
13.2 建議開發順序
階段	重點	交付檢查
Phase 1｜核心流程	服務說明、報名、申請狀態、管理者確認、固定分組及活動資訊。	能從報名走到取得活動資訊。
